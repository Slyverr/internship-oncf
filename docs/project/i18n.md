# Internationalization

## Current inventory — 2026-10-01

The i18n foundation has started, but the product is not translated end to end. This inventory distinguishes the code contract and error catalog from the remaining UI migration.

- The web app has 30 App Router `page.tsx` files across public/auth routes and the protected dashboard. The route families are authentication, dashboard, orders, programs, claims, customers, users, reports, notifications, and settings.
- There is no locale route segment or third-party translation runtime. The app uses a typed catalog/resolver because English is the only enabled locale. The root layout resolves the `ecommand-locale` cookie against `SUPPORTED_LOCALES`, sets the document `lang`, and passes the locale to the client LocaleProvider and `useTranslate` hook. Server route pages, the dashboard shell, and route metadata use `getRequestTranslator()` so their copy follows the same request locale. Unsupported or missing cookie values safely resolve to English. No locale choice is exposed yet because English is the only enabled locale. The English catalog is the source for auth, dashboard, orders, programs, claims, customers, users, reports, notifications, settings, and shared shell/control copy.
- `apps/web/src/i18n/messages/en.ts` contains the English copy. Call sites use stable nested references from `apps/web/src/i18n/message-keys.ts` (`Messages.*`) instead of embedding catalog paths in components. The alias test checks that every English catalog entry maps to exactly one stable reference, and the source scan rejects direct `translate("...path")` calls. To rename or reorganize a catalog path while preserving call sites, update the corresponding reference value in `message-keys.ts`.
- A TypeScript AST test scans web source for literal and interpolated JSX text, including conditional text branches and fallbacks; common user-facing attributes (`alt`, ARIA labels/descriptions, placeholders, and titles); UI-copy object properties and copy-named constants/defaults; and direct literals passed to common message helpers (`toast.success`, `setError`, browser alerts, and similar calls). Regression fixtures cover conditional JSX/helper copy and ensure customer names and developer logs are not mistaken for UI messages. It also checks that every validated request DTO field has a catalog label. Route metadata has a separate translated-title check. Explicit ONCF branding and typography samples are exempted. The scan also rejects client component calls to `translate()` that omit an explicit locale, and checks that locale-sensitive display formatters receive the active `locale` argument. The scan still cannot prove extraction for copy assembled through arbitrary project-specific helpers or server-side templates, so those remain separate review targets.
- The locale catalog parity check discovers catalog files, requires a one-to-one match with `SUPPORTED_LOCALES`, and verifies every enabled locale has the same message keys, message/plural shape, and interpolation variables as English. Keep a locale out of `SUPPORTED_LOCALES` until its complete catalog passes; plural categories may differ by language as long as the message has an `other` form and preserves the English interpolation contract.
- Workflow statuses, claim types, and claim priorities use explicit typed English-catalog maps. Unknown fixed codes resolve to localized safe labels; the previous generic title-casing helper has been removed so arbitrary API values are not presented as translated copy. Reference-data management lets admins create and rename units, goods types, goods, accessory operations, and rejection reasons. Their stored names are user-managed business data and are displayed verbatim; translate the surrounding field/column/action labels, not these names. If a seeded value needs a translated label, give it an immutable code and map that code to locale catalogs instead of inferring identity from its editable name.
- Locale formatting foundation started: shared date and number helpers use the English default locale for display dates, message times, month and relative-time labels, numeric values, and file sizes. Dashboard and claim-conversation components use the date helpers; date-fns relative time explicitly uses its English locale. Formatters accept a typed locale argument so approved locales can be added centrally later. Date-only workflow values preserve their calendar day across time zones; timestamps use the user's local time zone. A business time-zone policy and currency formatter remain open because no currency value is currently displayed.
- The API now has a global error response contract: `{ code, statusCode, details? }`. The NestJS validation pipe turns field validators into field-scoped rule codes, and the global exception filter removes backend-authored English messages before they reach clients. Invalid numeric IDs and public record codes now use the shared `INVALID_IDENTIFIER` code. Auth, registration-review, DTO validation, authorization, profile, and storage paths use stable codes instead of presentation prose. Notification provider diagnostics remain stored internally and are excluded from client response DTOs. The web maps every declared API error and response code through exhaustive typed records; unknown or dynamically generated domain codes retain a safe generic fallback.
- The translator supports typed nested catalog paths, named interpolation, and plural forms selected with `Intl.PluralRules` for the resolved locale. A catalog can provide an explicit `zero` form when that locale's plural category for zero needs different grammar. Count labels for pending registrations, customer portfolio selection, unread notifications, and claim-conversation actions use this shared plural path. Settings navigation, appearance option labels/descriptions, account fields, security guidance, sync status, and save/error feedback use the catalog. Notification page/popover controls, counts, accessibility labels, empty/loading/error states, toast feedback, system message templates, and order/program/claim statuses use the catalog. The public authentication family (login, registration, password recovery/reset, theme selector, and shared brand panel), order reports, claim-owned list/create/edit/detail/conversation copy, dashboard home, and order/program/customer workflows now use the catalog. User list filters and labels, create/edit validation and forms, review/deactivation actions, detail summaries, portfolio selection, and user selectors are also catalog-backed. Navigation names/layout switch labels, shared guided-form actions/progress, confirmation defaults, retry feedback, dialog/sheet close names, sidebar labels, breadcrumb/table accessibility copy, and good/unit selector states use catalog entries. Claim type/status/priority values have explicit locale maps rather than relying on title-casing; order/program/claim status label maps are shared by dashboard, record views, and notification presentation. Dashboard action visibility returns permission-approved actions without English labels, keeping access rules separate from localized UI. Shared attachment list/upload controls and the customer selector are catalog-backed. System notifications are stored and returned as message codes plus interpolation parameters; legacy English notification columns remain nullable for old rows and are not included in API responses. Older claim-comment notifications are mapped to the comment code during presentation. The password-reset email uses one API-owned English template for SMTP and the local `.eml` fallback; locale selection is not yet passed into email delivery. Fixed workflow values such as roles, statuses, claim types, and priorities are stable codes mapped to catalog keys with a localized unknown fallback. Editable operational names remain as stored and are not title-cased or machine-translated; localized labels for them require stable codes and reviewed translations. A web test checks that new pages do not silently fall back to the generic application title. The root title, title template, and description also use the catalog.

- Server-owned copy audit (2026-10-01): the NestJS exception filter strips framework and validator prose, returning stable API error codes and structured validation-rule codes; success DTOs return response codes. Web mappings cover the shared code sets, and tests verify that server-provided message strings are discarded. - Formatting audit (2026-10-01): application date, time, number, and file-size formatting is routed through shared locale-aware helpers. Direct `Intl` formatting is confined to those helpers and plural selection in the translator; fixed workflow enum labels have explicit catalog maps.
- Database-label boundary (2026-10-01): statuses and other fixed workflow values are code-mapped; customer, role-profile, user-authored, and admin-editable reference-data names are business data and display verbatim. They are not missing catalog strings, and the application must not auto-translate them. Seeded reference rows follow the same rule while administrators can rename them. If the product later requires localized names for managed reference rows, add stable codes and locale-specific labels with explicit per-locale edit behavior; never infer a translation key from a mutable name.

## French terminology baseline

Use Moroccan French for the French catalog and keep the product's business meaning ahead of literal English translations. ONCF's public Fret et Logistique pages use “demandes de transport,” “marchandises,” and “prestations accessoires”; its customer-care pages use “réclamation.” Apply those terms consistently to corresponding ECommand workflows. [ONCF Fret et Logistique](https://www.oncf.ma/fr/Fret-et-logistique) · [ONCF customer care](https://www.oncf.ma/fr/A-votre-ecoute)

- Translate the ECommand order workflow as “demande de transport” when the label refers to a customer's request to transport goods; avoid the literal “ordre” in that context.
- Use “marchandise(s)” for goods being transported and “prestation(s) accessoire(s)” for accessory services.
- Use “réclamation” for a customer's claim or complaint. Keep internal workflow statuses distinct from the user's message text.
- Keep ONCF, ECommand, ICE, DTM, and GSCWF unchanged. Preserve user-authored comments and admin-managed reference names verbatim.
- “Programme prévisionnel” appears in ONCF procurement material, but that does not establish it as the right name for this application's transport-planning program. Confirm the domain term against the internship requirements before choosing its French label.

These are translation starting points, not approval of the complete catalog. The French draft now has matching top-level sections for all 22 English catalog sections in `apps/web/src/i18n/drafts/fr.ts`. The expanded French draft now passes key, plural-shape, and interpolation-placeholder parity for 1,242 message keys across all 22 English sections. The earlier 417-key check through Orders is superseded. The parity test derives section coverage from the English catalog. A separate French password-reset email draft is in `apps/api/src/email/messages/fr-draft.ts`; it is not connected to delivery and still needs translation review. Structural parity does not establish translation quality: the French UI and email copy still require terminology review. Both drafts remain separate from runtime catalogs. Keep French disabled until all 1,253 English message strings, email text, and locale formatting have reviewed French equivalents.

## Locale implementation decision

- The typed resolver is request-aware on server and client routes. Keep the existing `Messages.*` aliases as stable catalog references when adding a locale; do not replace them with inline catalog paths.
- Do not add a locale preference column until a second locale is reviewed and enabled. When French is ready, add it to `SUPPORTED_LOCALES`, provide a complete `fr` catalog, and expose a locale choice that writes the same-site cookie. Persisting a locale before the runtime can render it would create a misleading preference.
- Keep English as the default and preserve existing unprefixed routes. For this authenticated operations portal, use the user's existing synced preference after sign-in and a locale cookie for public/login/registration screens. Do not add a locale field to user preferences until the runtime can actually render the selected locale.
- Continue using the device's local time zone for timestamps, matching current behavior; keep date-only workflow fields as calendar dates. There is no currency display to localize. Revisit the time-zone rule only if the business requirements introduce a fixed operational zone or users outside the current operating region.
- Treat French strings as a draft until an ONCF/domain reviewer approves rail and commercial terminology. Do not expose French selection until every application-owned catalog entry, email template, API error/response mapping, date/number formatter, and public metadata path has a French translation or an explicit approved fallback.

## Acceptance criteria

- Every application-owned label, action, helper, validation, error, empty/loading state, status label, notification template, and email template is available in each approved locale or has an explicit reviewed fallback.
- Locale selection survives refresh and follows the approved public/account persistence policy.
- Stored enum values, API contracts, database keys, and `ORD-` / `PRG-` / `CLM-` identifiers do not depend on translated copy.
- Formatting uses the selected locale consistently, and approved RTL layouts have no clipping, overflow, or reversed workflow semantics.
- Translation coverage and browser/API locale checks run automatically; captures document the final viewport review.

# Localization

## Current status

English is the only enabled locale. Application-owned web copy, route metadata, fixed workflow labels, validation feedback, API errors, success feedback, and system notifications use typed catalogs or stable codes. French is not enabled. The French UI and email files are drafts; structural parity does not mean the translations have been reviewed.

## Web message catalog

- English copy lives in apps/web/src/i18n/messages/en.ts.
- UI call sites use stable aliases from apps/web/src/i18n/message-keys.ts through the active translator. Do not put catalog paths or user-facing prose directly in components.
- The resolver and provider live in apps/web/src/i18n. The ecommand-locale cookie selects a supported locale; missing and unsupported values resolve to English. Routes remain unprefixed, and the root layout sets the document language.
- Use named interpolation for dynamic values and the shared plural API for counts. Keep date, time, number, and file-size formatting in the locale-aware helpers. Date-only workflow values must retain their calendar date; timestamps currently use the user's local time zone.
- Fixed workflow codes such as status, role, claim type, and priority require explicit catalog mappings. Never translate a stored value by title-casing it.
- Customer names, user-authored comments, and administrator-managed reference-data names are business data. Display them as entered; do not infer translation keys from editable names.

## API and notification contract

- API errors use the shared shape { code, statusCode, details? }. Validation details contain field paths and stable rule codes. The global exception filter removes NestJS and validator prose before responses reach the web app.
- Transport failures that receive no HTTP response use `API_TRANSPORT_ERROR_CODES.API_UNAVAILABLE` with status 503. The server-rendered error boundary preserves that code across Next.js and resolves display copy from the active catalog; it must not identify outages by comparing translated sentences.
- Mutation feedback uses shared response codes. Add a shared code and map it to catalog copy when the UI needs specific guidance.
- System notifications expose a stable message code and interpolation parameters. The web resolves their title and body from its catalog. Legacy notification prose is not returned to clients; user-authored claim comments remain authored text.
- Keep request and response DTOs, shared code definitions, OpenAPI schemas, and generated web clients aligned. Do not add display prose to API responses.

The API reset-password email has its own English catalog at apps/api/src/email/messages/en.ts, shared by SMTP and the local mailbox fallback. Email delivery is English-only until locale-aware sending is intentionally implemented.

## Automated checks

Run the web checks with bun run test and bun run typecheck from apps/web. Run API tests from apps/api or the root workspace commands.

The web checks verify catalog and alias parity, interpolation, translated route metadata, API code mappings, locale formatting calls, and static UI-copy patterns in JSX, common accessibility attributes, copy-named properties/constants, and common message helpers. API tests verify code-based errors and ensure exception prose is not exposed through response DTOs.

These checks cannot prove extraction when copy is assembled through an arbitrary project-specific helper or server-side template. Review new helper and template output when adding user-facing copy; keep the source in the relevant catalog.

## French rollout

Do not expose French until every application-owned UI and email message has reviewed French copy, all code mappings and metadata have translations or an approved fallback, and locale formatting has been checked in the rendered app.

- The draft UI catalog is apps/web/src/i18n/drafts/fr.ts. It passes key, plural-shape, and interpolation parity, but still needs Moroccan French and ONCF terminology review.
- The reset-email draft is apps/api/src/email/messages/fr-draft.ts and is not connected to delivery. The API email tests keep its keys, field types, and reset-link interpolation aligned with the English source.
- Use “demande de transport” for a customer's transport request, “marchandise” for transported goods, “prestation accessoire” for accessory services, and “réclamation” for a customer claim. Keep ONCF, ECommand, ICE, DTM, and GSCWF unchanged. Confirm the French term for the planning program against the internship requirements.
- After translation review, enable the locale in the supported-locale registry, add a user-facing locale choice, set document language correctly, and verify direct links, refresh, authentication, and formatting. Add locale to synced user preferences only when the runtime can render the selected locale. Keep English as the default and preserve existing routes.
- Arabic and right-to-left support are out of scope and need a separate layout review.

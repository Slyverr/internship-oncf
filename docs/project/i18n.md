# Internationalization

## Current inventory — 2026-09-30

Internationalization implementation has not started. This is a source inventory and delivery plan, not a claim that the app is translated.

- The web app has 30 App Router `page.tsx` files across public/auth routes and the protected dashboard. The route families are authentication, dashboard, orders, programs, claims, customers, users, reports, notifications, and settings.
- There is no translation/runtime package in `apps/web/package.json`, no locale route segment, and no message catalog. The root layout hardcodes `<html lang="en">`.
- User-visible copy is written directly in route and component JSX. Reusable components live under `apps/web/src/components`; there are currently 104 TSX component files, so a route-only migration would leave shared menus, forms, dialogs, empty/error states, and chat untranslated.
- `apps/web/src/lib/enum-labels.ts` humanizes underscore-separated values but is not a translation map. Database reference labels and API enum/status values need stable language-neutral keys before the UI can choose localized labels reliably.
- Locale formatting foundation started: `apps/web/src/lib/date-utils.ts` now exposes the English default locale and shared display-date, medium-date, message-time, month, and relative-time formatters. Dashboard and claim-conversation components use the shared helpers; date-fns relative time explicitly uses its English locale. The helpers accept a typed locale argument so approved locales can be added centrally later.
- API validation and business-rule messages can be shown in web forms. Email and notification copy are produced outside page components as well. Their UI-facing error mapping and authored-message policy must be covered; translating only JSX would leave mixed-language workflows.
- Appearance preferences sync per user, but currently contain only theme, font family, text size, motion, and workspace layout. There is no locale preference. If locale should follow the account across devices, extend the existing preference contract and its validation together rather than adding a separate client-only switch.

## Decisions to confirm

1. Initial locales. Keep English as the source language and fallback. French and Arabic are candidate additions for the Moroccan pilot; confirm which are required before building catalogs. Arabic requires right-to-left layout review across navigation, tables, forms, dialogs, chat, and directional icons.
2. Translation ownership and review. Name who approves terminology for rail/customer operations, status names, validation, email, and reports.
3. Locale persistence. Recommended: anonymous/public users use an explicit locale route or browser choice; signed-in users sync the choice through user preferences, with a stable default when no preference exists.
4. URL compatibility. Preserve current English URLs through a default-locale redirect or rewrite policy; avoid breaking bookmarked `/dashboard/...` routes when adding locale-aware routing.

## Implementation sequence

### Foundation progress — 2026-09-30

- Completed the first low-risk code step without adding a dependency or changing the current language: user-visible dates now resolve through an explicit English locale rather than the browser's ambient locale.
- Preserved the dashboard's medium date style, the existing list/detail date style, UTC month labels, and claim-chat time formats.
- Focused web tests, web typecheck, Biome, and fresh dashboard screenshots at 390px and 1440px passed. Captures are temporary under `/tmp/ecommand-i18n-format-review`.
- Remaining before broader locale support: confirm locale set and translation ownership, choose the message-catalog/runtime approach, add locale preference/routing, and migrate text/API validation/status catalogs by route family.

### P0 — Decide the contract

- Confirm initial locales, fallback, locale ownership, number/date/time-zone expectations, and whether public links carry a locale.
- Select a maintained, open-source App Router message-catalog approach. Keep it compatible with server and client components and avoid custom translation hooks scattered through pages.
- Define stable message namespaces by shared shell, authentication, common controls/errors, and domain route family. Keep database/API values and public record codes language-neutral.

### P1 — Build the foundation

- Add typed catalogs and a single locale resolver/provider integrated at the App Router boundary. Set both `lang` and `dir`; preserve the existing route surface for the default locale.
- Add a typed translation API usable by server and client components, with interpolation/plural support and a detectable missing-key fallback.
- Add one shared date, time, number, and relative-time formatter that always receives the resolved locale and an explicit business/user time-zone policy.
- Extend shared/API/web preference types and validation together if account-synced locale is approved. Keep the locale choice immediately responsive and use browser storage only as a startup/fallback cache.
- Map enums and reference-data codes to translation keys. Do not translate by rewriting stored status/catalog names or by title-casing arbitrary server strings.

### P1 — Migrate by workflow

1. Shared shell, navigation, notifications, common buttons/dialogs, loading/empty/error states.
2. Public authentication and registration/recovery flows, including API validation errors and outgoing recovery email templates.
3. Core client and agent workflows: orders, programs, and claims/conversation.
4. Customers, users/admin review, reports, settings, and remaining operational screens.
5. Notification templates and persisted notification presentation; keep user-authored messages unchanged and readable as authored.

Each route-family change should leave no hardcoded interface text in the migrated files, retain a source-language fallback, and add tests for catalog completeness and interpolation.

### P2 — Verify all locales

- Test route navigation, direct/deep links, refresh, authentication, preference sync, and API error mapping under every locale.
- Test pluralization and formatting for dates, times, numbers, percentages, and report exports.
- For RTL, test logical spacing/alignment, table scrolling, form order, chat bubbles, icons, and phone/tablet layouts. Do not mirror brand marks or non-directional icons.
- Add a CI check for missing/unused catalog keys and a browser screenshot matrix for every locale at phone, tablet, laptop, and ultrawide sizes.

## Acceptance criteria

- Every application-owned label, action, helper, validation, error, empty/loading state, status label, notification template, and email template is available in each approved locale or has an explicit reviewed fallback.
- Locale selection survives refresh and follows the approved public/account persistence policy.
- Stored enum values, API contracts, database keys, and `ORD-` / `PRG-` / `CLM-` identifiers do not depend on translated copy.
- Formatting uses the selected locale consistently, and approved RTL layouts have no clipping, overflow, or reversed workflow semantics.
- Translation coverage and browser/API locale checks run automatically; captures document the final viewport review.
